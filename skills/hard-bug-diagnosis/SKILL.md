# Hard Bug Diagnosis

用于复杂缺陷的有界诊断流程。先做轻量检查，只有现有证据不足以解释症状时才逐步深入。

## 诊断流程

1. **固定症状**：记录用户描述的预期、实际结果、触发条件和影响范围。已有信息足够时直接继续；只询问会改变诊断方向的缺失信息。
2. **收集现有证据**：先检查相关代码、调用链、状态变化、最近改动和已有日志。把观察到的事实与推测分开；不要盲目增加日志。
3. **列出可证伪的假设**：提出 2–4 个按证据排序的原因。每个假设写明预期能观察到什么，以及什么证据会推翻它。
4. **选择最小验证方式**：优先使用已有、低风险证据。默认不新增或运行测试，不编译、不启动服务、不发网络请求，也不操作共享或生产数据。上述操作只有在用户明确授权后才执行；授权后选择能区分当前假设的最小命令或复现路径。
5. **修复已被证据支持的根因**：只改完成修复所需的范围。不要把诊断顺带扩展成无关重构。临时调试代码必须在交付前清理。
6. **汇报结论与边界**：说明根因、修复、检查过的调用路径，以及哪些内容只做了静态检查、哪些运行验证没有执行。证据不足时明确保留不确定性，不把猜测写成结论。

## 约束

- 若需要运行命令、构建、测试、访问服务或更改数据才能继续，先说明具体操作及其诊断价值，等待用户明确授权。
- 处理日志、请求样本或业务数据时，只取定位所需的最小片段，并遮盖 token、个人信息和医疗信息。
- 如果无法在当前授权范围内区分假设，列出已经检查的证据和仍缺少的最小信息，然后向用户询问；不要为了完成流程而编造复现或根因。
- 对简单、已有明确原因的缺陷，直接按普通 bug 流程处理，不套用完整诊断流程。
