# Vue 3 应用开发工作流

开发页面、组件、表单、接口、路由、Pinia Store 或 H5 UI 时读取本文件。

## 先建立项目画像

检查 `package.json`、锁文件、构建配置和相似功能，记录实际使用的 Vue、Router、状态管理、请求库、UI 库、CSS 方案、目录结构和别名。依赖已存在才使用；未经要求不要安装替代库。

如果项目是移动 H5，还要确认：

- viewport/rem/px 转换策略；
- 安全区域和微信等宿主环境限制；
- UI 库的按需引入或全量注册方式；
- 返回键、滚动位置、键盘遮挡和弱网体验。

## 页面与组件拆分

- 页面组件负责路由级编排、数据加载和业务流程。
- 展示组件通过 props/emits 提供稳定边界，不直接依赖页面路由或全局请求实例。
- 弹窗与表单应明确打开、关闭、提交成功、取消和重置规则。
- 不要因为文件较长就机械拆分；当职责、复用或独立测试价值清晰时再提取组件。
- 先搜索项目已有组件、composable、格式化工具和 UI 模式，避免重复实现。

## 表单与交互状态

- 将展示值、提交值和接口模型的转换放在明确位置。
- 在提交前完成必要校验；提交期间禁用重复操作，并在 `finally` 中可靠恢复状态。
- 区分字段校验失败、业务失败、网络失败和系统异常，复用项目统一提示方式。
- 提交成功后根据业务选择关闭、清空、刷新局部数据或导航；不要同时进行相互冲突的状态更新。
- 处理加载、骨架、空数据、部分数据、失败、重试和无权限状态。

## API 与异步流程

- API 定义和拦截器留在项目现有请求层，页面不重复拼接鉴权或通用错误处理。
- 明确请求参数、响应模型和业务成功条件；不要通过 `any` 或无约束对象掩盖已知结构。
- 对搜索、切页、切换详情等可能竞态的请求，使用取消、序列号或失效标记，避免旧响应覆盖新状态。
- 组件卸载后不再提交无意义的 UI 状态；能由请求库取消时按项目方式取消。
- 不吞掉异常。若上层需要决定提示或流程，应保留错误传播语义。

## 状态管理

按最小范围选择状态位置：

1. 只服务于单个组件：组件内 `ref`/`reactive`。
2. 同一功能内多处复用的有状态逻辑：composable。
3. 跨页面共享、需要 Devtools 或持久生命周期的业务状态：项目现有 Store。
4. 远端服务数据：优先遵循项目已有缓存/请求方案，不自动复制进 Store。

新 Vue 3 项目在没有既定方案时可优先 Pinia；存量 Vuex 项目继续使用 Vuex，除非用户明确要求迁移。Store action 表达业务动作，避免让页面到处直接拼装复杂状态变更。

## 路由

- 使用项目现有 Vue Router 版本与约定；Vue Router 4 的 Composition API 中使用 `useRouter`、`useRoute` 和组合式导航守卫。
- 路由页面按项目规范动态导入；路由 meta 只承载稳定元数据，不塞入运行时业务对象。
- 权限判断集中在现有守卫或权限层；页面仍需处理无权限结果和后端拒绝。
- 监听 route 时只监听实际需要的字段，避免深度监听整个 route 对象。
- 导航前确认未保存表单、重复导航和异步初始化的处理方式。

## 样式与 UI

- 优先复用项目级 UI 库、设计令牌、字体、图标和间距体系。
- 保持样式作用域清晰；必须覆盖第三方组件时，限制选择器范围并说明原因。
- 检查长文本、极值数字、空值、小屏、横竖屏、滚动容器和内容溢出。
- 可访问性属于功能质量：交互元素应可识别，表单有明确标签，图片有适当替代文本，颜色不是唯一状态信号。
- 不用截图替代可实现的 UI，不为单个页面复制一套已有组件。

## 完成前自查

- props、emits、v-model 和插槽契约是否明确；
- ref/reactive 解构是否导致响应丢失；
- watcher、事件、定时器和请求是否有清理；
- 列表 key 是否稳定；
- 加载、空、错、禁用和重复提交状态是否闭环；
- 新增路由、Store、API 和样式是否沿用项目结构；
- 是否出现无关格式化、依赖升级或大范围重构。
